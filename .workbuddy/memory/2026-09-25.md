## 调研：把 ONNX/DML 组件统一到 Vulkan/CUDA 的可行性

**现状（三套运行时并存）**
- Talker + Predictor：llama.cpp GGUF，`inference/bin/` 只放了 Vulkan 版（`ggml-vulkan.dll`，无 `ggml-cuda.dll`）
- Decoder：ONNX Runtime + **DirectML**（`onnxruntime-directml==1.24.4`），跑在子进程 `workers/decoder.py`
- CodecEncoder / SpeakerEncoder：`encoder.py` 里 **硬编码 `CPUExecutionProvider`**，GUI 的 ONNX provider 选项对它们无效

**关键发现：llama.cpp b10621 已原生实现全套 Qwen3-TTS**
- `llama.dll` 导出 `llama_model_qwen3tts` / `llama_model_pockettts`，架构名 `qwen3tts`
- `mtmd.dll` 内含实现文件：`conformer.cpp`（说话人编码器）、`seanet_enc_stage/seanet_dec_stage`（codec 编解码器）、`rvq.codebook.*`、`code2wav`（波形解码器）、`mtmd_audio_preprocessor_qwen3tts_spk`（spk mel 前置）
- 高层管线 API：`mtmd_helper_gen_audio_init / set_input / step_prompt / step_gen / get_output / reset / free`、`mtmd_gen_audio_pipeline`
- 即：codec encoder / speaker encoder / codec decoder 都有现成 ggml 实现，可直接跑 Vulkan/CUDA；不用自己从零写 C++
- 限制：上游只支持 1.7B **Base**（不支持 CustomVoice/VoiceDesign）；GGUF 布局是 backbone + mmproj；seanet/code2wav 等子模块**不是导出符号**，只能整体走 mtmd 高层 API，或 fork llama.cpp 自行编译 DLL（会改变"用官方预编译 DLL"的分发方式）

**硬约束**
- ONNX Runtime **没有官方 Vulkan EP**（只有 CPU/CUDA/TensorRT/DML/WebGPU-Dawn 等）→ "全 Vulkan" 必须让三个 ONNX 模型离开 ORT
- 预编译 DLL 路线下无法往 llama.cpp 里加架构

**拷贝量推算（结论：不是瓶颈）**
- 每 80ms 帧：talker hidden D2H 8KB、predictor embedding H2D ~64KB、codes 128B、**decoder 状态往返 ~2.4MB×2（KV 8×2×1×16×72×64 fp16）**
- 合计 ≈4.9MB/帧 × 12.5fps ≈ **61MB/s**，约占 PCIe4.0 x16 的 0.25%
- 真痛点：两套运行时各自的显存池、DML 的 per-op 开销、ORT 每次 `run` 的 21 入/23 出 numpy 往返同步

**隐形成本**
- Decoder 现跑在子进程，与主进程 LLM **重叠并行**；若搬到同一张 GPU 会与 Talker/Predictor 抢 SM，可能反而拉高流式首音延迟

**结论**：文档 CLAUDE.md / readme.md 中"Encoder/Decoder: ONNX Runtime (DirectML/Cuda)"的描述需要更新

## 量化实测（新增脚本，2026-09-25）

新增两个诊断脚本（不入 git 的产物在 `output/profile/`）：
- `53-Profile-Breakdown.py` — 猴补丁插桩全链路耗时归因；`--compare A B` 对比两次结果；
  `--no-mask` 做消融；结果落 `output/profile/<tag>.json` + `<tag>.txt`
- `54-Probe-Logits-Latency.py` — `llama_get_logits_ith` 延迟最小复现 + 变体对照 + 双 context 交替复现

**实测数据（本机，model-base，30 字文本 → 5.68s 音频 / 71 帧）**
- 端到端 RTF ≈ **2.02**（readme 称 RTX5050 上 0.35，本机慢约 5.8 倍，需另查）
- 顶层：Predictor 循环 **10434 ms / 90.9%**；Talker 反馈步 498 ms / 4.3%；Talker 采样 8 ms / 0.1%
- Predictor 内部：采样 **9884 ms / 94.7%**，其中 `llama_get_logits_ith` **9735 ms（占全墙钟 85%）**；真正的图执行只有 412 ms / 3.9%

**已排除的假设（都做了 A/B 实验）**
1. ❌ Python 全词表掩码：`--no-mask` 把掩码和 get_logits_ith 全跳过 → 耗时**不降反平移**到原生 `llama_sampler_sample`（9884→9889 ms），墙钟 RTF 2.0198→2.0283 纹丝不动
2. ❌ DML / ONNX 干扰：`--onnx CPU` 彻底移除 DML 设备 → 生成循环 +0.1%（9735→9749 ms）
3. ❌ 跨模块拷贝量：状态张量往返 2.3MB × 2，memmove 实测 84 µs/次 @ 28 GB/s；全部 host 胶水合计仅 ~40 ms / 11.5 s（0.3%）
4. ❌ API 本身：孤立复现 `get_logits_ith` = **1.3 µs**，双 context 交替复刻 = **4.6 µs**，所有 n_ctx/embeddings/n_seq_max 变体都无差异

**机制判断**
- 该 Vulkan 构建下 `llama_decode` 是**异步提交**：GPU 真实执行时间不在 decode 里付，而是分摊到 host 首次读输出的地方
  - Talker：`decode_step` 7.0 ms，其中 llm_decode 仅 1.14 ms，其余 ~5.9 ms 付在 `get_embeddings()` 的 D2H 读回
  - Predictor：`llm_decode` 386 µs，其余 ~9 ms 付在 logits 读回
- **未能完全定位**为何孤立 1.3 µs、管线内 9 ms（差 ~7000 倍）。剩余候选：embd 输入路径、每帧 `clear_kv_cache()`、Vulkan 队列与设备级同步策略
- 下一步建议：换 CUDA 版 llama.cpp 二进制再跑 `--compare`（bin/ 目前只有 Vulkan）；显式测 `llama_synchronize`

**对"统一后端"的结论**
- 统一 ONNX→Vulkan/CUDA **不会提升性能**（瓶颈在 llama.cpp/Vulkan 侧的读回等待，不在 ONNX 侧）
- 其价值在工程层面：单一运行时、消除 DML 设备脆弱性（实测主进程再开一个 DML 会话会触发 `GetDeviceRemovedReason` 设备移除崩溃）、以及把两个 Encoder 从写死的 CPU 切到 GPU
- Decoder 维持子进程重叠并行（已确认不改成同卡）

## 续：GUI 批量快、ServerApi 单路慢 —— 根因定位并已修复（2026-09-25 下午）

### 触发问题
用户实测：GUI 批量 16 路 RTF **0.334**（LLM 0.286 / Decoder 0.046），但 ServerApi 单路克隆配音约 1 秒音频要 1 秒多。

### ⚠️ 修正上一节的错误结论
上一节第 4 条"孤立复现 `get_logits_ith` = 1.3 µs"**是无效量测**。
`54-Probe-Logits-Latency.py` 的 `ctx.decode()` 全部返回 **-1**（`log/ latest.log` 里刷屏
`decode: failed to initialize batch` + `init: ... inconsistent sequence positions ...
required that Y = X + 1`）。原因：`probe()` 反复用 `pos=0`（以及交替测试用 `pos=cs`）造成
位置不连续，llama.cpp 直接拒绝整批；于是 135 µs 是"失败调用"的耗时，logits 是陈旧数据。
**教训：任何 decode 探针必须断言返回值 rc==0，否则量到的是空转。**

### 决定性实测（新脚本，本机 = AMD RX 6750 GRE 10GB / Vulkan，无 NVIDIA）
- `55-Probe-Decode-Scaling.py` — decode / 首次读 logits（真实同步点）随批大小 B 的变化
  - predictor 每帧固定 16 次 decode（1 prefill + 15 步自回归），**调用次数与路数无关**
  - B=1: decode 414 µs + sync **9253 µs** → 每帧 157 ms → RTF **1.965**
  - B=16: decode 1482 µs + sync **14602 µs** → 每帧 267 ms
  - sync 只涨 58% 而工作量涨 16 倍 ⇒ **每次调用是固定开销**
  - 折算每路 RTF：B=1 → 1.965，B=16 → **0.208**，B=32 → 0.135（与用户 GUI 的 0.286 吻合）
  - 流水线深度测试：K=15 连续 decode 不读 logits → 每次仍 8.98 ms，说明 GPU 真的每次要 ~9 ms
- `56-Probe-Ctx-Params.py` — context 参数 A/B：**n_ctx / n_batch / embeddings / flash_attn 全部无效**；
  `offload_kqv=False` 反而更慢（decode 9387 + sync 3712 = 13.1 ms）；talker(1006MB) 也要 6.6 ms/次
- `57-Probe-Token-Scaling.py` — 单次调用内 token 数扫描（predictor）
  - 1 token = 9.70 ms，2 = 9.84，16 = 12.50，256 = 37.13，512 = 64.39
  - **16 次「1 token」调用 = 155.22 ms；1 次「16 token」调用 = 12.50 ms ⇒ 省 12.4x**
  - 这就是批量快的根本机制：把同样的 16 次调用摊到 16 路上
- `58-Probe-Predictor-Backend.py` — 换后端
  - predictor 放 Vulkan：每帧 156.52 ms（每次调用 9782 µs）→ RTF 1.956
  - predictor 放 **CPU**：每帧 **73.58 ms**（每次调用 4599 µs）→ RTF **0.920** ⇒ **CPU 快 2.13x**

### 结论
1. 瓶颈是 **predictor 每帧 16 次串行 llama_decode，每次在 Vulkan 上有 ~9.6 ms 固定开销**
   （与 batch 内 token 数几乎无关），不是算力、不是带宽、不是拷贝、不是 DML。
2. 单路 RTF ≈ 9.6 ms × 16 × 12.5 fps ≈ 1.9，被这个固定开销钉死。
3. 批量能摊薄它；单路只能**减少调用次数（做不到，自回归）或换设备**。
